# PocketCam

PocketCam is a consent-based remote Android camera monitor. The Android app publishes camera video over WebRTC; the browser dashboard receives it. The signaling service relays only authenticated WebRTC negotiation messages and never stores or proxies video.

## Current status

The repository now contains the initial monorepo foundation:

- `services/signaling-server`: Fastify health/auth/pairing endpoints, device authorization, revocation, TURN credentials, and authenticated Socket.IO signaling
- `apps/web`: React dashboard with login, pairing-code generation, device selection, real WebRTC offer/answer/ICE negotiation, snapshot, and browser recording controls
- `packages/shared-types`: shared protocol types
- `apps/android`: native Kotlin/Compose project with camera permission flow, foreground streaming notification, CameraX-compatible project dependencies, and WebRTC signaling/capture session code

The dashboard does not simulate a camera feed. It reports the actual peer connection state and only displays video after a real Android peer publishes a track.

## Different-network operation

LAN addresses such as `192.168.16.214` and `localhost` cannot work across the
internet. For remote operation, deploy the signaling service behind a public
DNS name with HTTPS/WSS and deploy Coturn with a public IP. The supplied
`infra/docker-compose.yml` runs signaling, Coturn, and Caddy. Set the values in
`.env`, point `SIGNALING_DOMAIN`, `DASHBOARD_DOMAIN`, and the dashboard's
`VITE_SIGNALING_URL` at your DNS names, then run
`docker compose -f infra/docker-compose.yml up -d --build` on a cloud VM.
The compose stack serves the dashboard and signaling service through Caddy,
which obtains certificates automatically for valid DNS records. Configure the
VM firewall for TCP 80/443, TURN 3478
TCP/UDP, TURN TLS 5349 TCP, and UDP relay ports 49160-49200.

The Android app's server URL must then be the HTTPS signaling URL, for example
`https://signaling.example.com`, not a LAN address. TURN credentials are
short-lived and generated by the signaling service; no TURN secret is sent to
the clients.

## Local development

```powershell
npm install
Copy-Item .env.example .env
npm run typecheck
npm test
npm run build
```

The signaling service build output is generated under `services/signaling-server/dist/src`. Android Studio can open `apps/android` directly. A Gradle executable and wrapper are not available on this machine, so the Android APK build must be run from Android Studio or after adding the Gradle wrapper.

Run the service and dashboard in separate terminals:

```powershell
npm --workspace @pocketcam/signaling-server run dev
npm --workspace @pocketcam/web run dev
```

The demo login defaults are deliberately development-only (`owner` / `change-me-now`). Set `DEMO_USERNAME`, `DEMO_PASSWORD`, and a strong `JWT_SECRET` before any deployment.

## Security and deployment

Deploy the signaling service and dashboard behind HTTPS. Configure `WEB_ORIGIN`, `JWT_SECRET`, `TURN_URLS`, and short-lived TURN credential issuance before production. A TURN server is required for reliable connectivity across restrictive networks; STUN alone is not sufficient.

The current pairing/device/session store is in memory and must be replaced with a persistent authenticated store before production. Do not expose the development login or use a public demo deployment. See `docs/security.md` for limitations and the required hardening checklist.

## Android prerequisites

Install Android Studio, an Android SDK, and a physical Android device with USB debugging enabled. The Android app must request camera permission, show a foreground-service notification while streaming, and require an explicit Start action. Cross-network testing additionally requires HTTPS/WSS and a configured TURN service.
